# Supabase inventory authority

Project: SagaFight (`ccqnbnhfxjrypamdbrlt`). Postgres owns inventory, equipment, Scoin balance and the inventory transaction history in `saga_inventory_internal`. Auth remains Supabase Auth. Match/statistics/season/mail delivery and transport state remain D1/Render; this is a bounded inventory migration, not a migration of all game systems.

The six private tables are wallets, items, loadouts, events, migration_backups and config. RLS and explicit deny policies block browser roles. A public SECURITY INVOKER RPC delegates to a private SECURITY DEFINER function with an empty search path and a server credential check. All SQL is static; the API accepts only enumerated inventory actions, not SQL. Only the SHA-256 hash of a random 256-bit server credential is stored in the private config table. Store the credential as the Sites runtime secret `SAGA_INVENTORY_KEY`; never in Git, browser code or a request log. Existing SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY are reused. No service-role key is exposed or required. The schema reference is `supabase/inventory.sql`; provision the matching config hash securely after installing it on a new project.

D1 migration 0006 initially sets mode=legacy. A credential-protected internal migration endpoint freezes buys/equipment, copies accounts in batches of 10, writes immutable original snapshots in Postgres, verifies balances/ownership/equipment and activates Supabase only when all users have been imported. Keep D1 data intact; no source rows are deleted. Do not manually reset inventory_storage_control after cutover. No deploy/startup seeds overwrite an existing wallet.

Future rewards still pass game validation in D1; its reward ledger acts as an outbox. Postgres imports each event by (user,kind,source) once. Local delivery markers are recorded only after remote commit. A failed acknowledgement can be retried without duplicate Scoin. Claimed gifts similarly reconcile idempotently; admin purchases remain free. Purchases, reward reconciliation and balance checks share one locked wallet transaction. Repeated buys charge once. Equip requires ownership. Online loadouts are read from Supabase.

Once activated, missing runtime credentials or remote failure return errors; code refuses to read an older D1 bag as a fallback. Render already proxies account APIs through this Site, so both game URLs use the same Supabase inventory. GitHub updates do not modify the database or runtime secret.

Validation: live Postgres RPC tests cover original snapshot preservation, repeated bootstrap, concurrent duplicate buys, equip ownership, insufficient funds, idempotent rewards/gifts, free admin purchases and wrong credentials. Local integration covers maintenance/cutover, D1 purchase isolation, PvE reward delivery, lost delivery acknowledgement, remote outage and absent runtime credentials. Security advisors leave only the unrelated pre-existing leaked-password-protection warning.

Recovery: retain both D1 source data and Supabase migration_backups. They preserve state at the migration boundary; they do not represent purchases made after cutover. Back up the current Postgres database for later recovery. Never restore the old snapshot over a current wallet without reconciling later events. Deleted Render SQLite records from before this migration cannot be inferred from these sources.
